# Source ownership

Per-feature notes on which files own each behavior, which migrations a slice added and which seam tests cover it. Placement rules live in [`structure.md`](../structure.md); product behavior and Testing Decisions live in the owning spec. Read the entry for the feature you change, and update it in the same change when ownership moves or a slice adds owning files.

Tags source ownership is split across the API contract (`packages/api/src/tags.ts`), the PostgreSQL schema (`packages/db/src/schema/tags.ts`), the server boundary (`apps/server/src/features/tags/server/`), and the web surface (`apps/web/src/features/tags/`).

Documents source ownership is split across the API contracts (`packages/api/src/documents.ts`, `packages/api/src/document-templates.ts`, `packages/api/src/document-transfers.ts`), the empty-heading starter skeleton catalog shared with Project Shell (`packages/api/src/document-skeletons.ts`), the PostgreSQL schemas and versioned migrations (`packages/db/src/schema/document.ts`, `packages/db/src/schema/document-template.ts`, `packages/db/src/migrations/`), the server boundary (`apps/server/src/features/documents/server/`), and the Project Documents surface (`apps/web/src/features/documents/`). Document Templates use the Documents mutation boundary, not Work Templates or a template marketplace. Project/Wiki transfers reuse that boundary in `document-transfer-database.ts`, the shared row converter `document-row.ts`, and the shared `document-transfer-form.tsx`; they do not introduce another Document store.

Documents owns the dictionary-rename counterpart in `server/document-tag-rename-database.ts`; Tags calls it in the same transaction without owning Markdown parsing. Folder/parent navigation and previewed organization/Archive controls live in `document-navigation.tsx` and `document-organization-controls.tsx` (its dialog form is `ui/forms/document-organization-form.tsx`) beside the Project Documents surface.

Migration infrastructure is owned by `packages/db/scripts/`: `migration-repository.ts` validates canonical metadata, `check-migrations.ts` compares configured source schemas, `migration-target.ts` resolves and connects the application-aligned target, `migration-history.ts` verifies applied history, `schema-inspection.ts` reads physical catalog shape, `doctor.ts` exposes strict read-only readiness and explicit development compatibility, `development-lease.ts` holds and monitors shared runtime migration locks, and `migrate.ts` is the controlled write boundary. `prepare.ts` orchestrates issue database readiness through source checks, deep checks of both targets, and sequential canonical migrations; `prepare.test.ts` owns its orchestration and CLI seam. `packages/db/schema-files.ts` is the schema-file manifest shared by both Drizzle configs and source checks. Script type checking lives in `packages/db/tsconfig.scripts.json`; command integration tests use disposable databases in `packages/db/scripts/migrations.integration.test.ts` and `packages/db/scripts/prepare.integration.test.ts`. `scripts/local-dev.ts` owns Conductor/root task startup and the optional local PostgreSQL proxy; `scripts/local-dev-command.ts` owns task/help forwarding. The direct server `dev` command uses `scripts/dev-server.ts` to acquire the lease and `scripts/development-session.ts` to retry the lease once after `db:prepare` and to supervise and stop the API when verification fails. The contract and testing decisions live in `docs/tech-stack.md`, not a product feature spec.

Personal Wiki owns the authenticated ownership shell under `apps/web/src/features/personal-wiki/` and `apps/web/src/routes/_auth/personal-wiki.tsx`. It consumes the same Documents surface, contract, schema, server access, and mutations; Wiki Documents have Workspace ownership and no Project. Publishing remains a separate feature.

Personal Wiki's scope-selection and badge counterpart lives in `lib/document-scope.ts` and `ui/components/document-scope-badge.tsx`. Documents navigation consumes it to keep mixed results in separate ownership groups before Folder/hierarchy navigation; scope filters never create a new home. Record Discovery consumes it through `apps/web/src/features/record-discovery/ui/components/` for the founder chrome's `Search` and `All Documents` views. `packages/api/src/record-discovery.ts` owns the Document discovery and Universal Search contracts plus match context; `server/document-discovery-database.ts` queries authorized canonical Documents through the Documents access counterpart, while `universal-search-database.ts` queries the canonical Work, Project source record, Technical Diagram, Document, and File Attachment tables under Account ownership. `universal-search-results.tsx` renders the mixed-record Search results, and `context-record-preview.tsx` owns the shared `Open source record` action and session-only preview panel consumed by the current Kanban, Unified Calendar, Roadmap, Scope Tree, and Smart Collection surfaces. Discovery is not a Wiki-owned index or a new storage home.

The Documents in-memory edit session lives in `apps/web/src/features/documents/store/`; its Conflict Draft comparison and resolution surface lives in `ui/components/document-conflict-drafts.tsx`. The session consumes Client Shell connection state without creating persistent storage or a write queue. Client Shell's server support-response boundary preserves the validated Documents conflict payload while retaining its no-retry policy.

Technical Diagram structural model (spec 59 #421): `packages/api/src/technical-diagram-structure.ts` owns the typed canonical model of the three types (strict zod schemas per type: closed Architecture catalog with typed links, designed PostgreSQL Data Model, Sequence participants/messages/limited control groups with an optional exact Architecture node bind whose nullable `versionId` pins a Diagram Version), `resolveStructuralModel`, `diagramGraph` (read-only element projection for views, cards and the canvas), and the deterministic `canonicalStructuralModel`. Types live in `packages/db/src/schema/technical-diagram.ts`; the model stays in `technical_diagram.model` jsonb, validated per type at every write, and coordinates live only in `diagram_view.layout` (migration `0152`, expand-only). `saveTechnicalDiagramStructure` and `saveDiagramLayout` are the only edit commands; no DSL, Mermaid, SQL or DBML is a second source and no SQL is emitted (60). Web: `technical-diagram-outline.tsx` (structured outline), `technical-diagram-editor.tsx` with `lib/technical-diagram-edit.ts`, and `technical-diagram-canvas.tsx` (React Flow view).

Technical Diagram Views and Versions (spec 59 #422, migration `0153`, expand-only): `packages/api/src/technical-diagram-version.ts` owns `DIAGRAM_VERSION_LABELS`, the strict create (name plus confirmation key, no model or mode) and restore (shown `expectedRevision`) inputs, `createCheckpoint`, `restoreFromCheckpoint`, `diagramVersionReference` (the exact reference other specs pin) and `assertVersionBind`. `diagram_version` (`packages/db/src/schema/technical-diagram.ts`) is append-only with a copied model and no update path; `technical_diagram.revision` is the live revision that model saves and restores advance; `diagram_view` keeps ids and layout only, re-derived per edit through `pruneDiagramViewSelection`: the built-in `Default` view always selects the whole live element set (so a `Live` card that names no view keeps following added nodes) while a named view keeps its author's selection and only prunes deleted elements. `technical-diagrams-database.ts` adds `createVersion`, `listVersions`, `getVersion` and `restoreVersion`; every confirming command finds its prior result by the confirmation key on a lost concurrent insert instead of erroring (ADR-0004). the router exposes `createDiagramVersion`, `technicalDiagramVersions`, `technicalDiagramVersion` and `restoreDiagramVersion`, and a lifeline bind with `versionId` is checked against that checkpoint. Web: `diagram-version-panel.tsx` and the version choice in `technical-diagram-editor.tsx`; Playwright journey `apps/web/e2e/technical-diagrams.e2e.ts`.

Technical Diagram live cards and composition (spec 59 #423, migration `0154`, expand-only): `packages/api/src/technical-diagram-card.ts` owns `DIAGRAM_CARD_LABELS` (`Live`, `Exact`, `Convert to record and link`), `pinDiagramToVersion` and `diagramCardProjection` (the one read-only projection a Document or Project Wall card draws, so a card holds a source identity and never copies elements), the record-card inputs (identity plus position only, closed to `Work`, `Decision`, `Risk`, `Open Question`) and the previewed `Convert to record and link` plan (`buildConvertToRecordPlan`, `isSameConvertToRecordPlan`: target type, fields, exact `Diagram Version` and origin; the diagram and its authority mode are never written). `TechnicalDiagramSource.exactVersion` is set only when a card reads a checkpoint. The Project Wall pins through `project_wall_item.diagram_version_id` (`setCardPin`, `ProjectWallDiagrams.getVersion`; null is `Live`). `diagram_record_card` and `diagram_record_link` (`packages/db/src/schema/technical-diagram.ts`) hold canvas record cards and the record opened from a node of one exact version; `technicalDiagramRecordCards`, `placeDiagramRecordCard`, `moveDiagramRecordCard`, `removeDiagramRecordCard`, `previewDiagramNodeConversion` and `convertDiagramNodeToRecord` live on `TechnicalDiagramsAccess`; the one record is born through `insertConvertedRecord` and `readRecordRows` is reused from the User Flow store. Web: `diagram-composition-panel.tsx`, record cards in `technical-diagram-canvas.tsx`, the pin control in `project-wall-card.tsx` and the `Diagram Version` choice in the Documents insert panel. Surfaces 51 and 31 call these commands and open no second model.

Technical Diagram Mermaid conversion (spec 59 #424, no migration): `packages/api/src/technical-diagram-mermaid.ts` owns `MERMAID_CONVERT_LABELS`, the exact fenced-block reader, the pure block outcome (`Keep independent` leaves the body untouched; `Replace with live reference` swaps only the chosen block for `:::live-diagram{...}`) and `describeMermaidConversion` (source Document and version, block line, `Originates from` relation, block effect, Document revision after, every lost line, `roundTripSync: false`). `previewConversion` and `convert` in `technical-diagrams-database.ts` apply it in one transaction (new `Imported Independent Copy`, `diagram_document_origin`, default view, optional replacement with the Document revision increment and the `Live block` usage link); the diagram id is the confirmation key, so a retry returns the same diagram. Five-Minute Presentation Cluster (#465; no schema, no migration): the pure, clock-free clustering contract lives in `packages/api/src/project-activity-cluster.ts` (`withProjectActivityGroups`, `projectActivityEntriesOfRows`, `clusterProjectActivityRows`, `PROJECT_ACTIVITY_CLUSTER_WINDOW_MS`; imported by the web through `@cantiara/api/project-activity-cluster`), over the atomic rows of `packages/api/src/project-activity.ts`, exposed as `entries` (single rows and clusters) next to `rows`; a cluster carries every atomic row, so the ungrouped list stays derivable. Window rule, the chosen reading of 'within five minutes': each row within five minutes of the PRECEDING row of the same cluster (chaining), not five minutes after the cluster's first row. The cluster key also holds the origin source id and delivery id of a source-origin row, so different GitHub sources or deliveries never share a cluster. Clustering runs over the UNFILTERED sequence of the record scope first and stamps every row with a `group`; the event-type and source-type filters then narrow rows, so a hidden Status change, Archive or undo still closes a cluster and rows never merge across it. A cluster shows the rows that match the filters (two or more, otherwise a single row) and a cluster with no matching row does not appear. Same actor kind, actor id, origin kind and source record are required; only Field change rows without a redaction mark, without `undoOf` and with no undo kind other than `field` may cluster. Create, Status change, Archive, Relation, Automation event types, undo entries and structural undo boundaries stay their own rows and close an open cluster of that record (System automation rows are all typed Automation, so they never cluster).
