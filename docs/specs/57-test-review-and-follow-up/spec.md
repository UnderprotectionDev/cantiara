# Test İnceleme ve Takip

Kaynak: [`docs/workflow/57-test-review-and-follow-up/phase-context.md`](../../workflow/57-test-review-and-follow-up/phase-context.md)

## Problem Statement

Kurucu ürün dışında koşulmuş testlerin incelemesini, düzeltmesini ve takipini Test Oturumu ile Oturum Testi üzerinde ayrı ayrı yönetmek ister. Bugün rapor kabulü tarihsel bildirimi kaydeder ama inceleme hükmü, düzeltme/geri çekme/redaksiyon olayı, yerine-geçme, çelişki ve Özellik/Proje Sürümü özeti yoktur. Yeni olay geçmiş sonucu siler gibi görünür; oturumu kapatmak alt maddeleri örtük bitirir; çelişki son yazanı kazandırır; özet coverage veya yayın kapısı gibi okunur. Test Açığı, Test değerlendirmesi ve rapor kabulü bu sorunun parçası değildir.

## Solution

Kurucu Test Oturumu incelemesi ile her Oturum Testi incelemesini bağımsız tamamlar. İnceleme bildirilen sonucun üzerine yönetim kararı ekler; ham sonucu değiştirmez ve yayın kapısı veya Proje Sürümü sonucu değildir. Düzeltme, geri çekme ve güvenlik redaksiyonu yeni olaydır; geçmiş bildirim silinmez. Çelişen veya bağlamı değişen sonuç kullanıcı değerlendirmesine taşınır; sistem kazanan seçmez ve Test Açığı üretmez. Özellik ve Proje Sürümü test özeti senaryo, Handoff, sonuç, açık ve değerlendirme kaynaklarına açılan nötr manzaradır; coverage, kalite puanı veya yayın kapısı üretmez ve Sürüm Kanıt Paketinin yerine geçmez. Testler alanı PRD’deki türetilmiş yönetim bölümleriyle mevcut kayıtları gösterir; faz veya CI panosu değildir.

## User Stories

1. As a founder, I want a Test Oturumu to start as `Unreviewed`, so that a newly accepted report is a management task rather than an already-judged result.
2. As a founder, I want to set a Test Oturumu to `Reviewed`, `Follow-up needed`, or `Closed` without changing any Oturum Testi review state, so that session housekeeping is not a silent bulk close.
3. As a founder, I want to set an Oturum Testi to `Reviewed`, `Follow-up needed`, or `Closed` without closing its parent Test Oturumu, so that item review is independent of session review.
4. As a founder, I want review state to leave the reported raw and normalized result untouched, so that a management judgment cannot masquerade as a new test run, a release gate, or a Proje Sürümü result.
5. As a founder closing a session that still has `Unreviewed` or `Follow-up needed` items, I want the remaining exact records shown and an optional close reason kept, so that incomplete review is visible rather than a gate.
6. As a founder, I want an explicit `Mark session and selected results as reviewed` action that previews the exact records it will change and applies them in one auditable mutation, so that bulk review is never implicit.
7. As a founder, I want a later correction, withdrawal, redaction, or new relation not to silently reopen or rewind an existing review state, so that history stays additive; I want a `New context after close` signal instead.
8. As a founder, I want Handoff status to stay independent of Test Oturumu and Oturum Testi review, so that a returned report can only suggest `Result received` and cannot close, reopen, or retarget the Handoff.
9. As a founder who later learns a reported result was wrong, I want to add a reasoned `Correction` or `Withdrawal` event bound to the original record, so that the current view can surface the correction without deleting the original report.
10. As a founder reading a corrected item, I want to see why it was corrected and the chain of change, so that I can explain the history to myself later.
11. As a founder who finds a secret or personal data in a historical test record, I want security redaction to replace the sensitive value with a redaction mark, time, reason, and actor, so that the value cannot be used as current evidence or export while the audit trail remains.
12. As a founder, I do not want redaction to be Trash, account-closure redaction UI, or rewriting the original report in place, so that test history stays a history of events.
13. As a founder with one wrong Oturum Testi, I want Correction or Withdrawal rather than trashing that item alone, so that Oturum Testi never gains an independent archive/Trash life (77 applies the unit; this surface must not offer a child-only delete).
14. As a founder, I want to create a directed `Supersedes` / `Superseded` relation between exact Oturum Testi records of the same specialist type, so that a later validation can replace the current summary without erasing the old result.
15. As a founder, I want that relation to be acyclic and not to change either historical result value, so that superseding is provenance, not a rewrite.
16. As a founder looking at the same Planlı Test Senaryosu version with different normalized results and no superseding relation, I want a `test-result-conflict` attention signal, so that I must judge which result stands.
17. As a founder, I want that signal to be derived only from an exact shared scenario version or an explicit relation plus differing normalized results, so that title similarity cannot invent a conflict or pick a winner.
18. As a founder, I want the conflict signal to close only when I bind a valid result, so that last-write-wins never silently resolves history.
19. As a founder, I want a `Context changed` signal when a bound Birincil spec version changed or recorded branch/commit/build no longer matches the target context, so that I can reassess without the old result being marked failed or stale by the clock.
20. As a founder, I do not want mere elapsed time or an unrelated new commit to produce staleness, so that the product does not pretend to do semantic code impact analysis.
21. As a founder looking at a `Failed`, `Blocked`, or `Inconclusive` result, I want no automatic Bug, İş, Risk, Açık Soru, Karar, notification, or priority, so that follow-up stays a conscious act.
22. As a founder, I want `Create follow-up work` to preview the target record, initial values, `Originates from` on the owning Test Oturumu, and immutable `Origin Location` on the exact Oturum Testi before commit, so that origin is exact.
23. As a founder, I want several results to attach to one existing İş when they share a root cause, so that closing that İş does not rewrite historical results to `Passed`.
24. As a founder, I want verifying a fix to require a new Test Oturumu and, if I choose, a superseding relation, so that a closed Bug cannot launder old failures.
25. As a founder on a Feature, I want a live neutral summary of related Planlı Test Senaryosu records, Handoff'lar, Test Oturumu and Oturum Testi records, open Test Açığı records, follow-up work, and the latest Test değerlendirmesi, so that I can read the test landscape in one place.
26. As a founder on a Proje Sürümü, I want the same summary derived from in-scope Feature/İş relations plus direct Proje Sürümü links, so that release context is not a second test database.
27. As a founder reading that summary, I want each number to open the exact record set and filters that produced it, so that a count is never a score.
28. As a founder, I want the summary to keep raw and normalized results, source session, executor, reporter, time, and technical context, so that GitHub checks stay a separate external fact and are not converted into Test Oturumu records.
29. As a founder, I want missing tests, context change, conflict, `Failed` / `Blocked` / `Inconclusive` / `Skipped` results, unreviewed reports, open Test Açığı records, or post-assessment new context to appear as source-linked neutral attention, so that the product does not issue a pass/fail, coverage, quality score, test waiver, or release gate.
30. As a founder, I do not want this Feature/Proje Sürümü summary to stand in for a Sürüm Kanıt Paketi, so that release-readiness evaluation stays on its own surface.
31. As a founder, I do not want the Tests area to be a project phase, CI dashboard, or producer of new test truth, so that it only manages existing records.
32. As a founder in the Tests area, I want live derived sections for unreviewed reports, follow-up needed results, open/planned Test Açığı records, conflicting or awaiting-supersede results, context-changed results, active Handoffs, recent Test Oturumu records, and recent Test değerlendirmesi records, so that management is one source-linked view rather than a phase or CI dashboard.
33. As a founder, I do not want conflict, context-change, or a failed result to auto-create a Test Açığı, so that gap records stay a user decision owned by the Test Gaps feature.
34. As a founder, I do not want a Test değerlendirmesi snapshot to be rewritten here, so that assessment remains a dated snapshot owned by the Test Assessments feature; this surface only opens it.
35. As a founder using only a keyboard or a screen reader, I want to complete review, correction, superseding, follow-up preview, and summary drill-down, so that the closed accessibility journey “test raporu inceleme” is possible.
36. As a founder, I want English UI copy for review states and the bulk-review action, so that product language stays English while locale remains formatting only.

## Implementation Decisions

- **Owning documents.** Behavior is owned by [Manuel kayıt ve inceleme durumlarının bağımsızlığı](../../prd/10-testing-and-validation.md#manuel-kayıt-ve-inceleme-durumlarının-bağımsızlığı), [Düzeltme, geri çekme ve güvenlik redaksiyonu](../../prd/10-testing-and-validation.md#düzeltme-geri-çekme-ve-güvenlik-redaksiyonu), [Yerine geçen doğrulama ve çelişki](../../prd/10-testing-and-validation.md#yerine-geçen-doğrulama-ve-çelişki), [Bağlam değişikliği](../../prd/10-testing-and-validation.md#bağlam-değişikliği), [Takip işi ve ilişkili kayıtlar](../../prd/10-testing-and-validation.md#takip-işi-ve-ilişkili-kayıtlar), and [Özellik, Proje Sürümü ve ortak kayıt davranışı](../../prd/10-testing-and-validation.md#özellik-proje-sürümü-ve-ortak-kayıt-davranışı). Review states and Oturum Testi as a owned component are [ana kayıt türleri](../../prd/02-domain-model-and-lifecycle.md#ana-kayıt-türleri-ve-asgari-sözleşmeler). `Yerine geçer` / `Yerine geçildi` is the standard relation in [standart ilişki türleri](../../prd/02-domain-model-and-lifecycle.md#standart-ilişki-türleri). Security redaction mechanism is owned by PRD 13; this feature only applies it to test history presentation. No new ADR: historical integrity versus silent rewrite is already decided in PRD 10 and [ADR-0007](../../adr/0007-surum-kaniti-guven-modeli.md) (reported Test Oturumu is not release evidence).
- **Glossary.** Use Test Oturumu, Oturum Testi, Düzeltme / geri çekme / redaksiyon olayı, `Yerine geçer` / `Yerine geçildi`, Test Açığı (opened, not created here), Test değerlendirmesi (opened, not rewritten here), Kökeni, Köken konumu, Dikkat sinyali, Güvenlik redaksiyonu. Do not introduce last-write-wins, coverage score, quality score, release gate, CI dashboard, Tests as a phase, or a second summary record. Test Açığı is not this card's sub-work; Test değerlendirmesi is not this card's sub-work.
- **One seam.** Test Review — the product-facing interface for session/item review, correction/withdrawal/redaction events, superseding, conflict/context signals, follow-up-work preview, the Tests area derived management view, and the Feature/Proje Sürümü neutral summary. Report ingest stays on the Test Report Acceptance seam (54). Gap create/close stays on Test Gaps (55). Assessment snapshots stay on Test Assessments (56). Release Evidence Pack stays on 64.
- **Independent review.** Test Oturumu and each Oturum Testi have separate review states: `Unreviewed`, `Reviewed`, `Follow-up needed`, `Closed`. Closing a session with remaining `Unreviewed` or `Follow-up needed` items is allowed after preview; remaining items stay as they are. Bulk `Mark session and selected results as reviewed` previews exact records and commits one auditable mutation. Review never mutates reported raw or normalized results. Review is not a publish gate and does not write Proje Sürümü status. This surface must not offer archive/Trash of a single Oturum Testi; the session plus items are one historical unit (77 applies that unit).
- **Additive events.** Correction and withdrawal append a reasoned event bound to the original record. Current view promotes the correction; original report and chain remain in audit history. Security redaction shows a mark, time, reason, and actor instead of content; redacted evidence cannot be used for current evaluation or export. Redaction is not Trash, account-closure redaction UI, or in-place rewrite of the original report.
- **Superseding and conflict.** `Supersedes` / `Superseded` is the existing directed acyclic same-type relation between exact Oturum Testi records. New result does not delete or rewrite the old. Absent that relation, same exact scenario version plus differing normalized results produces `test-result-conflict`. The product never picks a winner. Binding a valid result closes the signal. Text similarity does not match tests. Conflict, context-change, and failed results do not create a Test Açığı.
- **Context changed.** Signal only when a bound Birincil spec version changed or recorded branch/commit/build no longer matches the target context. It does not mark the old result invalid, failed, or stale; it does not create a Test Açığı or a new Handoff. Elapsed time or an unrelated commit is not staleness. Missing technical context on a manual result is shown as unknown, not as semantic impact analysis.
- **Follow-up.** `Failed`, `Blocked`, or `Inconclusive` create no Bug, İş, Risk, Açık Soru, Karar, notification, or priority. `Create follow-up work` previews target, initial values, `Originates from` on the Test Oturumu, and `Origin Location` on the exact Oturum Testi. Multiple results may attach to one existing İş. Closing that İş does not rewrite historical results; verification needs a new Test Oturumu and optional superseding.
- **Neutral summary.** Feature summary is a live derived view of openly related scenarios, Handoffs, sessions/items, open Test Açığı records, follow-up work, and the latest Test değerlendirmesi. Proje Sürümü summary uses in-scope Feature/İş relations plus direct Proje Sürümü links. Every count opens its exact record set. GitHub checks remain external facts. Missing tests, context change, conflict, `Failed` / `Blocked` / `Inconclusive` / `Skipped`, unreviewed reports, open Gaps, or post-assessment new context are source-linked attention — not a score or gate. The summary is not a Sürüm Kanıt Paketi. The Tests area is the same seam’s project management view: live derived sections named in PRD 10 (unreviewed reports, follow-up needed, open/planned Gaps, conflicting or awaiting-supersede, context-changed, active Handoffs, recent sessions, recent assessments). Counts open exact records. It does not produce new test truth, a phase, or a CI dashboard. 53/54/55/56 remain writers of their records; this view only lists them.
- **English UI labels.** First user-visible copy uses: `Unreviewed`, `Reviewed`, `Follow-up needed`, `Closed`, `Mark session and selected results as reviewed`, `Correction`, `Withdrawal`, `Supersedes`, `Create follow-up work`, `Context changed`, `New context after close`. Missing labels are added to the PRD term table in the same change that first shows them. No Turkish UI.
- **Observability.** Review, correction, withdrawal, superseding, and follow-up-work creation are **Kayıt geçmişi**. Security redaction may also emit a contentless **Denetim kaydı** mark. Do not label the review/correction chain as Denetim kaydı. Secrets never enter search, export, or logs.

## Testing Decisions

- **What a good test is.** Tests observe Test Review through its public interface: review-state commands, bulk preview/commit, correction/withdrawal/redaction events, superseding relations, conflict/context signals, follow-up-work preview, Tests area section drill-down, and Feature/Proje Sürümü summary drill-down. They do not assert Prisma row shapes or recompute a coverage formula. Expected values are product rules (independence of session vs item, additive events, no auto-gap, counts open exact sets).
- **Seam (one).** Test Review. Report ingest, Test Açığı write, Test değerlendirmesi write, and Release Evidence Pack are counterparts: this suite may assert they are not invoked or not rewritten.
- **Modules under test.** Test Review only. Playwright for the closed accessibility journey “test raporu inceleme” is the same seam observed through the UI.
- **Prior art.** No Vitest/Playwright suite yet beyond Account Access. Contract tests live at this seam with fixture Test Oturumu / Oturum Testi records (as if already accepted by 54). Synthetic fixtures are allowed for event mechanics; the [Test geçmişi](../../prd/16-product-acceptance.md#uctan-uca-kabul-yolculuklari) journey requires a real project.
- **Required counterparts.** Review does not mutate reported results; closing a session does not close items; last-write-wins does not resolve conflict; binding a valid result closes the conflict signal; elapsed time is not staleness; failed result, conflict, or context-change does not create Test Açığı; summary does not emit a score or gate; summary is not a Sürüm Kanıt Paketi; Tests area is not a phase or CI dashboard; a single Oturum Testi cannot be trashed or archived alone.

## Out of Scope

- Test raporu kabulü (manuel/MCP/dosya zarfı, idempotency, secret tarama) — 54.
- Test Açığı oluşturma ve kapanış semantiği — 55; bu feature yalnız özet ve çelişkide açığı açar, üretmez.
- Test değerlendirmesi snapshot yazımı — 56; bu feature yalnız son snapshot'ı açar ve yeni bağlam sinyalini gösterir.
- Sürüm Kanıt Paketi, yayın skoru, yayın kapısı — 64.
- GitHub check'ini Test Oturumuna çevirme — 61.
- Planlı Test Senaryosu / Test Handoff'u yazımı — 53.
- Hesap kapatma veya güvenlik redaksiyonu UI'sinin teyit kartı — 78; bu feature yalnız test tarihçesine redaksiyon işaretini uygular.
- Testleri faz, CI panosu veya test runner yapmak.
