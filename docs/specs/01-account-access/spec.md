# Hesap Erişimi ve Oturum Güvenliği

Kaynak: [`docs/workflow/01-account-access/phase-context.md`](../../workflow/01-account-access/phase-context.md)

## Problem Statement

Kurucu Cantiara'ya GitHub kimliğiyle güvenli girmek, tek Çalışma Alanında kalmak ve hangi cihazların yazabildiğini denetlemek ister. Bugün iskelet e-posta/şifre girişine ve `SameSite=none` çerezine yaslanır; GitHub kimliği Hesaba bağlanmaz, Çalışma Alanı oluşmaz, oturum listesi/iptali ve yüksek risk teyidi yoktur. Repository yetkisi, ziyaretçi paylaşımı ve hesap kapatma bu sorunun parçası değildir; kapatma ve redaksiyon ise bu feature'ın teyidini bekler.

## Solution

Kurucu yalnız GitHub ile girer. Değişmez GitHub kullanıcı kimliği Hesaba bağlanır ve ilk girişte tek Çalışma Alanı oluşur. Web çerezi ile Tauri bearer'ı aynı oturum politikasını paylaşır; kurucu cihaz ve son etkinlikle oturumları listeler ve iptal eder. GitHub kesintisi mevcut geçerli oturumu sessizce düşürmez. `Confirm GitHub Identity` aynı değişmez kimliğe kısa ömürlü, tek kullanımlık yüksek risk yetkisi verir; tüketen feature'lar ayrı teyit kartı açmaz.

## User Stories

1. As a founder, I want to sign in with GitHub and no other identity provider, so that my Hesap is bound to one immutable GitHub user identity.
2. As a founder signing in for the first time, I want the product to create my Hesap and its single Çalışma Alanı together, so that successful sign-in lands me in an authorized working boundary rather than an empty identity.
3. As a founder signing in again with the same GitHub identity, I want to re-enter the same Hesap and Çalışma Alanı, so that a second Workspace or merged Account is never created.
4. As a founder, I want GitHub repository install, repo selection, and issue writing to stay off the sign-in path, so that identity is not confused with development authority.
5. As a founder who revoked GitHub login OAuth, I want every product session to end and the next sign-in to require GitHub consent again, so that removing login authority actually stops product access.
6. As a founder who uninstalled the GitHub App from a repository, I want my Hesap identity and valid product sessions to keep working, so that development disconnect does not lock me out.
7. As a founder looking at a failed sign-in, I want the error not to reveal whether a Hesap or Çalışma Alanı exists, so that attackers cannot enumerate accounts.
8. As a founder (and as the operator of the service), I want sign-in start and callback to be rate-limited by IP and by Hesap identity, so that callback flooding and credential stuffing are contained.
9. As a founder on the web, I want the session cookie to be `Secure`, `HttpOnly`, and `SameSite=Lax`, so that the browser cannot leak the session to a casual third-party request.
10. As a founder on the web, I want cookie-authenticated state-changing requests to be CSRF-protected, so that another site cannot revoke or mint access in my name.
11. As a founder on macOS Tauri, I want GitHub sign-in to open in the system browser and return only a one-time short-lived code over the deep link, so that session and GitHub tokens never appear in a URL.
12. As a founder on macOS Tauri, I want that code to be exchanged server-side for a revocable Better Auth bearer session token stored in Stronghold, so that the desktop shell uses the same product session as the web.
13. As a founder, I want web and Tauri sessions to share one idle and absolute lifetime (12 hours idle, 30 days from creation), so that the shell is not a second security policy.
14. As a founder, I want to see active sessions with device and last-activity information, so that I can recognize an unexpected device.
15. As a founder, I want to revoke one session or all other sessions, so that a lost device stops writing immediately.
16. As a founder whose session was revoked, I want subsequent writes from that session to fail closed, so that revocation is not cosmetic.
17. As a founder signed in during a GitHub outage, I want my still-valid product session to keep reading and writing private product data until it expires, so that GitHub being down is not a silent logout.
18. As a founder signed in during a GitHub outage, I want that session's lifetime not to be extended, so that an outage cannot become an unbounded access window.
19. As a founder during a GitHub outage, I want new sign-in and `Confirm GitHub Identity` to wait visibly and high-risk actions that need the grant to stay blocked, so that destructive work cannot skip GitHub proof.
20. As a founder during a GitHub outage, I want access-reducing actions such as session revoke to keep working, so that I can still shut a device down.
21. As a founder about to close the Hesap, redact security-sensitive content, permanently delete early, or erase personal data, I want `Confirm GitHub Identity` to run a fresh GitHub OAuth authorization-code tour with PKCE and `prompt=select_account`, so that an old session or another provider cannot authorize destruction.
22. As a founder completing that tour, I want the product to accept the grant only when the returned immutable GitHub user identity matches the current Hesap, so that a different GitHub user cannot confirm in my name.
23. As a founder, I want that grant to be one-time, bound to the intended operation, and valid for at most 10 minutes, so that leftover confirmation cannot be reused.
24. As a founder (and as an attacker replaying a callback), I want a different identity, expired tour, state/PKCE failure, or reused grant to be rejected with no high-risk write, so that confirmation failures fail closed.
25. As a founder, I want `Confirm GitHub Identity` not to be presented as a password, MFA, or GitHub forcing new credentials, so that the UI tells the truth about what is being proved.
26. As a consuming feature (Hesap kapatma, güvenlik redaksiyonu, erken kalıcı silme, kişisel veri silme), I want to call this grant instead of opening a second confirmation card, so that high-risk proof stays one product behavior.
27. As a consuming feature, I still want the typed Account or Project name confirmation to stay in my own flow, so that GitHub proof and name-typing remain distinct steps owned by the destructive action.
28. As a founder, I want login, session, and confirmation events to be recorded as Denetim kaydı without secrets, so that access can be explained later without leaking tokens.
29. As the operator restoring from backup, I want session revoke to be a restore-replayable irreversible security event, so that an old database copy cannot resurrect a revoked session.
30. As a founder, I want English UI copy for sign-in, sessions, revoke, and `Confirm GitHub Identity`, so that the product language stays English while locale remains a later preferences feature.
31. As a founder using only a keyboard or a screen reader, I want to complete sign-in, session listing, revoke, and `Confirm GitHub Identity`, so that the closed accessibility journey “Giriş ve oturum” is possible.
32. As a founder, I do not want email/password, magic link, extra identity providers, team invites, or Account merging, so that the first product stays a single-founder GitHub boundary.
33. As a founder, I do not want a visitor Paylaşım erişim oturumu to be treated as my product session, so that link-sharing cannot inherit Workspace writes.
34. As a founder, I do not want this feature to close the Hesap, install a GitHub App, or host the redaction/personal-data UI, so that those journeys remain their own features while reusing this grant.

## Implementation Decisions

- **Owning documents.** Behavior is owned by [Hesap ve Çalışma Alanı](../../prd/03-account-platform-operations.md#hesap-ve-calisma-alani), [Oturum güvenliği](../../prd/03-account-platform-operations.md#oturum-guvenligi), and [GitHub kimliğini yeniden teyit etme](../../prd/03-account-platform-operations.md#github-kimliğini-yeniden-teyit-etme). Hesap / Çalışma Alanı ownership is [kapsam ve sahiplik](../../prd/02-domain-model-and-lifecycle.md#kapsam-ve-sahiplik). Login OAuth versus GitHub App is [ADR-0006](../../adr/0006-github-entegrasyon-guven-siniri.md). Session revoke replay is [ADR-0003](../../adr/0003-restore-guvenlik-olay-gunlugu.md) and [ADR-0019](../../adr/0019-guvenlik-olay-gunlugunu-ve-ust-anahtari-ayri-guven-alaninda-tut.md). Visitor sessions are owned by sharing, not this feature; see [ADR-0002](../../adr/0002-dis-erisim-guvenlik-siniri.md). No new ADR: the surprising boundaries are already decided.
- **Glossary.** Use Hesap, Çalışma Alanı, GitHub kimliğini yeniden teyit etme (`Confirm GitHub Identity`), GitHub bağlantısı (out of this feature), Paylaşım erişim oturumu (must not be treated as a founder session), Denetim kaydı, and Geri döndürülemez güvenlik olay günlüğü. Do not introduce User Workspace, profile project, organization, team, re-authentication, MFA, password verification, or general session refresh. Session records live in Hesap scope; they are not a second ownership boundary.
- **Identity module.** Better Auth remains the identity and product-session runtime (tech stack). Email/password is disabled. The only sign-in provider is GitHub login OAuth. The Hesap's immutable identity is GitHub's stable user id, not email, username, or repository id.
- **Login versus App.** GitHub login OAuth requests only identity scopes needed to bind the Hesap. It must not request repository install, Contents, Issues, or other App permissions. GitHub App installation is a later GitHub bağlantısı feature; this module must not consult App installation when deciding whether a product session is valid.
- **Hesap and Çalışma Alanı on first sign-in.** The first successful GitHub callback that does not already map to a Hesap creates the Hesap and its single Çalışma Alanı in one success path. A later callback with the same GitHub user id reuses that pair. No second Çalışma Alanı, transfer, or team membership UI is created here. Workspace overview, projects, and preferences stay in their own features; this feature only needs the authorization boundary so a valid session is admitted to that Workspace.
- **Web session.** Web sessions are cookies with `Secure`, `HttpOnly`, and `SameSite=Lax` (the current scaffold's `SameSite=none` plus email/password is not product behavior). Cookie-authenticated state-changing requests use CSRF protection. Session and GitHub tokens are never written into URLs.
- **Tauri session.** Packaged Tauri opens GitHub in the system browser (Opener). The deep link carries only a one-time, short-lived code. The backend exchanges that code for a revocable Better Auth bearer session token. The token is stored in Tauri Stronghold. Web and Tauri share idle 12 hours and absolute 30 days from creation; shell is not a policy fork. Signing, notarization, updater, and online-only empty-state UX stay in the web/macOS client feature.
- **Session list and revoke.** The founder can list sessions with device and last-activity fields, revoke one session, or revoke all other sessions. A revoked session cannot perform further writes. Session tokens are Secret: they never enter search, export, or logs.
- **GitHub login OAuth removal.** Revoking GitHub login OAuth ends product sessions and forces a new OAuth consent on the next sign-in. It does not revoke a GitHub App installation or its historical records (those records are out of this feature; the invariant is simply that login revocation must not be implemented as App uninstallation, and App uninstallation must not be implemented as session kill).
- **GitHub outage.** If GitHub is unreachable, an already-valid product session continues ordinary private read/write until its existing expiry; expiry is not extended. New sign-in and `Confirm GitHub Identity` wait visibly. High-risk actions that require the grant are not applied. Access-reducing actions (session revoke; later external-surface revoke) are not blocked by GitHub unavailability. GitHub eşitlemesi waiting UI belongs to the GitHub bağlantısı feature; this feature's duty is not to drop the product session when GitHub cannot be reached.
- **`Confirm GitHub Identity`.** The product starts a new OAuth authorization-code tour with PKCE and `prompt=select_account`. Callback GitHub user id must equal the current Hesap. Success mints a one-time server grant, at most 10 minutes, bound to the intended operation identifier supplied by the caller. Different identity, expired tour, state/PKCE error, or reuse rejects with no high-risk write. The action is not copy-written as password, MFA, or GitHub forcing new credentials. Application-level MFA stays out of the first product; if GitHub confirmation cannot complete, high-risk work stays fail-closed.
- **Grant consumption.** This feature owns start, callback, grant mint, and single-use consume. Consuming features (Hesap kapatma, güvenlik redaksiyonu, erken kalıcı silme, kişisel veri silme) pass an operation identifier, consume the grant, and keep their own typed-name confirmation. They must not ship a second identity-proof card. This feature may include a test-only consume path so the grant is verifiable before those features exist; that path must not be a product high-risk action.
- **Observability.** Sign-in, sign-out, session revoke, confirmation start/success/failure are Denetim kaydı events (365-day auth/authorization class) with aliased identities and no tokens, emails as secrets, or private content. Failed sign-in responses stay generic. User-visible errors follow the secret-free support-reference rule without implementing the client-shell error surface.
- **Restore replay for revoke.** Session revoke is an irreversible security action. It must append a secret-free, identity-aliased event to the Geri döndürülemez güvenlik olay günlüğü through an append/replay interface, and a test must show that replaying the event after a restored still-live session row keeps that session unauthorized. The production log store must not live in the primary restore unit; see [ADR-0019](../../adr/0019-guvenlik-olay-gunlugunu-ve-ust-anahtari-ayri-guven-alaninda-tut.md). Full RPO/RTO, alarms, and operator runbooks stay in the operator-backup feature; this feature ships the revoke event type, the append/replay contract, and a durable adapter that is not the primary database (a dedicated test database is acceptable in CI).
- **English UI labels.** First user-visible copy for this feature uses: `Continue with GitHub`, `Sign Out`, `Sessions`, `Revoke Session`, `Revoke Other Sessions`, `Confirm GitHub Identity`. `Confirm GitHub Identity` is already in the PRD term table; the others are added to that table in the same change that first shows them. No Turkish UI. Locale/time-zone preference UI is the account-preferences feature.
- **Rate limiting.** Application-level limits on GitHub sign-in start and callback are scoped to IP and Hesap identity. Edge WAF is complementary, not a substitute for the Hesap-identity dimension.
- **Envelope encryption.** GitHub login tokens, if stored, follow the existing secret classification and envelope-encryption rule; they are not written as domain fields.

## Testing Decisions

- **What a good test is.** Tests observe Account Access through its public interface: GitHub sign-in start/callback, current session, session list/revoke, Tauri code exchange, `Confirm GitHub Identity` start/callback/consume, and whether a protected product command is authorized. They do not assert Better Auth internals, Prisma row shapes, or mock private collaborators. Expected values are product rules (GitHub user id match, 10-minute grant, 12-hour idle, generic failure copy), not recomputed implementation.
- **Seam (one).** Account Access — the product-facing identity and session interface used by the web app, the Tauri shell, and later consumers of `Confirm GitHub Identity`. GitHub OAuth and the security-event log are adapters behind that interface (real versus test double). Playwright for the closed accessibility journey “Giriş ve oturum” is the same seam observed through the UI, not a second product module.
- **Modules under test.** Account Access only. Workspace overview, GitHub App, sharing visitor sessions, Hesap kapatma, redaction, and personal-data packages are not in this suite except as “this command is unauthorized / this grant is missing” counterparts.
- **Prior art.** The repository has no Vitest/Playwright suite yet. First contract tests live at this seam with a GitHub OAuth test double and a security-event log test double that still exercises append/replay. Synthetic fixture is the evidence environment for [Hesap ve kişisel veri](../../prd/16-product-acceptance.md#uctan-uca-kabul-yolculuklari). Cloud tests must not use production sessions, tokens, or private user content.
- **Required counterparts.** Email/password and magic-link routes absent; repository scopes absent from login OAuth; failed sign-in does not distinguish unknown versus known identity; revoked session cannot write; reused or mismatched confirmation grant cannot write; GitHub-down does not drop a valid session and does not extend it; App-uninstall signal does not kill sessions; visitor sharing session cannot call founder session revoke.

## Out of Scope

- E-posta/şifre, sihirli bağlantı, başka kimlik sağlayıcı, çoklu Hesap birleştirme, kurtarma anahtarı, ad-hoc Hesap yeniden bağlama, uygulama düzeyi MFA, ekip daveti.
- Girişle birlikte GitHub App kurma, repository seçme, issue yazma, webhook veya geliştirme kaydı eşitlemesi.
- Paylaşım ziyaretçisi oturumunu kurucu oturumu sayma; Dış yüzey cookie'si veya parola kapısı.
- Hesap kapatma penceresi, kapanma dondurması, Çalışma Alanı çıkış paketi, güvenlik redaksiyonu UI'si, kişisel veri dışa aktarma/silme UI'si, erken kalıcı silme UI'si — bunlar bu grant'i tüketir, burada inşa edilmez.
- Hesap profil tercihleri (locale, saat dilimi, görünüm), online-only boş durum ve yazılmamış risk UI'si, Tauri imza/notarization/updater, AB bölge kullanıcı yüzeyi, operasyonel yedek RPO/RTO ve hizmet alarmı.
- Windows Tauri, self-host, çevrimdışı kuyruk, uzantı giriş UI'si.

## Further Notes

- **Orient.** Glossary: Hesap, Çalışma Alanı, GitHub kimliğini yeniden teyit etme. Owning PRD: `docs/prd/03-account-platform-operations.md` (Hesap ve Çalışma Alanı, Oturum güvenliği). ADRs in play: 0006 (login OAuth vs App), 0003 and 0019 (session revoke replay), 0002 (visitor access is not this session). Related but not owning: PRD 12 (App), PRD 13 (consumes the grant; session token is Secret), PRD 14 (Paylaşım erişim oturumu), PRD 15 (availability SLI and accessibility), PRD 16 (journey), PRD 19 (MFA out of scope).
- **Acceptance.** Bind this feature to [Hesap ve kişisel veri](../../prd/16-product-acceptance.md#uctan-uca-kabul-yolculuklari) (synthetic fixture: new OAuth authorization-code + PKCE with `prompt=select_account`; identity mismatch, replay, and expiry counterparts) and to the closed manual accessibility journey **Giriş ve oturum**. Session lifetime, revoke, GitHub-outage continuation, and login-versus-App independence are in the same journey's account/session package even when kapatma/export UI is delivered later. Negative bounds (no email/password, no MFA, no login-time App install) are 19-class counterparts on that journey.
- **Consumers.** Workflows `78-security-redaction`, `81-personal-data`, and `84-account-closure` must call this grant. They do not copy the confirmation card. Typed-name confirmation stays in those features.
- **Scaffold debt.** Replacing email/password and `SameSite=none` is in-scope product correction for this feature, not a separate cleanup epic.
